# プレイテストと品質確認

操作可能な成果物を作成・変更したときに読む。今回は何を確認するかを先に選び、ルールの正しさ、操作して遊べること、狙った体験を区別して確かめる。

## 証拠と結論を対応させる

| 方法 | 確認できること | この方法だけで結論づけないこと |
| --- | --- | --- |
| 静的検査・構文確認 | 読み込める構造、型や参照の問題など | 入力・状態遷移・画面の実動作 |
| 単体・統合テスト | 指定した条件でのルールや処理の結果 | 操作感、読みやすさ、面白さ |
| headless・自動操作 | 実行した経路の動作、再現可能な回帰確認 | 見ていない描画、聞いていない音、人の判断 |
| 実際のプレイ | 実行した操作、状態遷移、表示・反応 | 未実行の端末や操作、人全般の評価 |
| 想定プレイヤーの観察 | その人の理解、選択、詰まり、感想 | 全ユーザーへの一般化 |

実行手段がないときも可能な検査を進め、確認できなかった操作・描画・音・対象環境を具体的に伝える。予定した確認やチェックリストを実行済みの結果として報告しない。

## 今回必要な経路を選ぶ

新規ゲームでは、起動から操作方法の理解、核となる行動、結果・区切り、次のプレイへ進める流れを通す。勝敗のないゲームでは、依頼された発見・創作・進行などを確認する。

既存ゲームの変更では、再現操作、変更した処理、隣接する状態や入力を中心にする。無関係な全機能の検査を毎回必須にしない。

必要なものだけ選ぶ。

- 終了条件の到達、結果の重複、終了後の入力、再開始の初期化。
- ポーズ、画面切り替え、フォーカス喪失・復帰、押しっぱなしや連打。
- 衝突、画面端、高速移動、同時イベント、生成位置の重なり。
- ランダム生成の妥当性、到達可能性、資源枯渇、ターンや時間の境界。
- 保存・読み込みと欠損・破損・旧データ。保存機能がある場合だけ扱う。
- 対象入力方式、解像度、縦横比、文字量、音量設定など変更に関係する条件。

再開始やシーンの寿命を変更した場合は反復して試し、処理、イベント、生成物、音が増えないかを観察する。

## 再現可能な不具合確認

不具合は、環境と版、初期状態、再現操作、期待結果、実際の結果に分ける。ランダム性が関わる場合はseedや再現できる入力を保持する。seedを固定していない場合、見た結果だけを同じ条件の比較に使わない。

修正後は同じ操作で確認する。境界条件や状態の競合など繰り返し起こる不具合には、適切な層へ小さな回帰テストを追加する。描画や単純な文言変更に、実装をなぞるだけのテストを増やさない。

自動操作が失敗した場合は、ゲームの不具合、テストの操作条件、使用ツールの制約を分けて調べる。テストを通すためだけにユーザー向けの挙動を変えない。

## 体験を観察する

面白さは自己評価の断言にせず、企画で狙った体験に沿って観察する。

| 観点 | 見ること |
| --- | --- |
| 理解 | 目標、操作、成功・失敗の理由を分かるか |
| 選択 | 行動を選ぶ手掛かりと、結果の違いがあるか |
| 反応 | 入力と反応が合い、次にできる操作が分かるか |
| 変化 | 同じ行動の反復に、学習・発見・展開があるか |
| 詰まり | 不公平な失敗、進行不能、不要な待ち時間があるか |

AIによるプレイ確認と、人によるプレイテストを区別する。人の評価が得られない場合は、ルール上の分析と操作の観察を伝え、想定プレイヤーが楽しめたと報告しない。

調整は、観察した問題、原因の仮説、変更する項目を対応させる。以前の状態と比較できる条件を使い、必要な検証が成功したら、新しい変更や懸念がない限り繰り返し検査を広げない。

## ゲーム画面としてのUI/UXを確認する

新規画面やUI/UXの変更では、実際のプレイ対象がある代表場面を表示し、次の観点で画面と操作を確かめる。静止画の構成確認と、操作・時間変化の確認を分け、見ていない場面を確認済みとしない。

| 観点 | 確認すること | 問題があれば見直すこと |
| --- | --- | --- |
| 画面の主役 | 世界・盤面・手札・会話など、今遊ぶ対象へ注意が向くか | 大きな見出し、指標カード、常設パネルが主面を圧迫していないか |
| 画角と縮尺 | 主役の大きさ、必要な判断範囲、文字や操作対象の読み取りやすさを保てるか | 全要素を収めるための引いたカメラ、広すぎる画角、対象や文字の一括縮小 |
| 見せない範囲 | 画面外・見切れ・場面限定表示にする要素を、役割に応じて選べているか | 見切れをすべて直す処理、詳細の常設、操作対象や必要な予告の欠落 |
| 判断と視線 | 対象、手掛かり、操作、結果を意図した速度で追えるか | 離れた情報への往復、過剰な強調、予告の見落とし |
| 状況に合う情報 | 通常・選択・危険・結果の各状態で必要なものが読めるか | すべての情報の常時表示、判断材料の隠しすぎ、表示の重なり |
| 操作の見通し | 選択状態、可能な行動、取り消し、効果の予測が実動作と合うか | 押せるように見えるだけの要素、説明に頼る操作、予測との不一致 |
| 結果と反応 | 成功・失敗や状態変化を、起きた場所と結び付けて理解できるか | 通知・ログだけの反応、遅すぎる表示、強い演出による遮蔽 |
| 画面間の流れ | 初回の操作から結果・再挑戦まで、迷いや不要な待ちがないか | 毎回の長い説明、操作の持ち越し、復帰時の文脈の喪失 |
| 対象入力と読み取り | 指やカーソルによる遮蔽、フォーカス、文字や色の識別を扱えるか | ホバーへの依存、小さい操作領域、色・音・演出だけの手掛かり |
| 作品の一貫性 | 主面、HUD、メニュー、音の表現が狙った体験につながるか | 汎用部品の混在、読めない装飾、遊びと関係しない効果 |

「サイドバーや指標カードが整然と並び、ゲームがその一部の小さな表示になっている」場合は、[見た目と音の設計](見た目と音の設計.md#業務アプリの構成をそのまま使わない)の基準で各要素の役割を再確認する。カードや表が中心でも、その配置・比較・操作が遊びを生むゲームなら維持する。見た目の印象だけで必要な情報を削らない。

画角や配置を変更した場合は、対象が増えた場面、画面端、対象解像度・縦横比など関係する条件で確認する。全表示のために主役が小さくなった場合は、[見せる範囲と見せない範囲](見た目と音の設計.md#見せる範囲と見せない範囲を決める)へ戻り、表示範囲・場面限定表示・配置を先に見直す。全体表示が必要な盤面や明示された要件は維持し、必要な手掛かりが隠れた場合は読み取れるように修正する。

画面を派手にする前に、主面を中心とする構成、情報の出す時機、操作と結果のつながりを直す。通常時の一枚だけで終えず、変更に関係する選択・危険・結果・再開などの状態を対象入力で確認する。UIを実際に表示・操作できない場合は、構成案やコード上の判断と、未確認の見え方・操作を区別する。

## 性能と対象環境

性能目標は対象端末とゲームの要件から決め、特定のFPSや解像度をすべてのゲームへ強制しない。重い代表場面で、フレーム時間、入力の遅れ、メモリ、読み込み、連続プレイ時の変化を必要な範囲で測る。

問題がある場合は計測して支配的な原因を探し、描画、物理、生成、音、データ処理など該当箇所を調整する。推測だけでオブジェクトプールや複雑な最適化を導入しない。

## 結果を共有する

試した操作と結果、修正した問題、残る問題、未確認項目を簡潔に伝える。依頼された完成条件との関係を示し、単に「テストOK」とまとめない。継続作業に必要な再現手順は既存の適切な場所に残すが、報告用Markdownを毎回新設しない。
