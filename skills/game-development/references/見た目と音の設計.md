# 見た目と音の設計

画面、UI、素材、アニメーション、音、演出を作成・変更するときに読む。ゲームのルールを理解でき、操作の結果が伝わる見せ方を、その作品の方向性に合わせて設計する。

## 体験に合わせて方向を決める

既存作品や指定された参考の、情報の優先順、色・形・質感、画面密度、動き、音の役割を確認する。ジャンル名だけでピクセルアート、ネオン、派手なエフェクトなどへ固定しない。

方向が未定で仕上がりに大きく影響する場合は、遊びと目的に結び付く少数の案を提示する。指定がある場合はその方向を具体化し、通常の細かな素材・配置・タイミングで承認を繰り返さない。

代表場面で、何を主役にし、何を背景にし、どの情報をいつ見せるかを決める。プレイ中、メニュー、結果画面で同じ情報を同じ強さで並べる必要はない。

## 判断に必要な情報を見せる

- プレイヤー、操作対象、目標、危険、獲得できるものを、色だけでなく形・位置・動きなどでも見分けられるようにする。
- HUDには今の判断に必要な値を優先する。数値が変化した理由と、次に取れる行動が分かる表示を選ぶ。
- 操作説明は実際の割り当てと対応させ、プレイを始めるための情報を最初に出す。必要な場面で説明を増やし、全ルールを長文で一度に提示しない。
- メニューとダイアログはフォーカス、選択、決定・戻るの反応を確認する。マウスを使わない入力が対象なら、その方式で最後まで操作できるようにする。
- 対象解像度、縦横比、文字の長さ、表示言語、端末の安全領域に合わせて配置を確かめる。拡大縮小したときの文字・操作領域・ゲーム内座標の関係を扱う。

ゲーム内の情報と、開発用のデバッグ表示や内部構成の説明を区別する。開発者向け情報をプレイヤーの通常画面へ残さない。

## 行動と結果の反応を組み立てる

重要な行動について、入力の受理、予兆、実行、成功・失敗、その後の状態をどう見せるかを考える。すべての段階に効果を付けるのではなく、分かりにくい箇所と体験の見せ場へ集中する。

| 目的 | 確認する関係 |
| --- | --- |
| 操作の反応 | 入力を受理した時点と画面の反応が合っているか |
| 危険の予告 | 回避や判断が必要な時間に、必要な情報が見えるか |
| 成功・失敗 | 判定と表示・音が一致し、色や音だけに依存していないか |
| 重みや勢い | 動き、音、カメラの反応が狙った感覚を支えているか |
| 次の行動 | 演出の待ち時間や表示の重なりが操作を妨げていないか |

ヒットストップ、画面の揺れ、残像、点滅などを使う場合は、目的と実際の変化を短く説明する。すべてのゲームで使う前提にせず、強度、頻度、操作への影響を確認する。強い揺れや点滅、重要な音には、必要に応じて低減・代替表示・音量調整を用意する。

## 素材を制作し、ゲームへ組み込む

既存・提供素材を確認し、足りない用途に合う素材を用意する。生成ツールが利用可能なら使えるが、任意のサービスを必須にしない。

スプライトなら透過、基準点、サイズ、向き、コマ間の一貫性、3D素材ならスケール、座標、マテリアル、リグなど、組み込みに必要な条件を先に決める。見栄えの良い一枚絵を、アニメーションや当たり判定にそのまま使える素材とみなさない。

UIの重要な文字や数値は、変更・翻訳・読みやすさに対応できるゲーム側の表示を優先する。素材を取り込んだ後、実際の背景、縮尺、動きの中で見え方を確認する。描画・読み込み負荷とメモリ量は対象環境に合わせて測る。

素材の出典と利用条件を、プロジェクトの既存の管理方法に合わせて保持する。出所不明の素材を配布物へ混ぜない。仮素材を使った確認と最終素材での確認を区別する。

## 音を画面と合わせる

行動音、環境音、BGM、声の役割を決め、同時に鳴る場合の優先順と音量を調整する。連打や多数の敵で効果音が重なり続ける場合は再生数や頻度を扱い、音の停止・フェードを状態遷移と合わせる。

音の再生開始にユーザー操作が必要な環境では、実際の起動から試す。ポーズ、ミュート、画面切り替え、再開始で意図した再生状態になるかを確かめる。再生できる手段がない場合は、音を聞いて確認したことにしない。

画面と音の反応は[プレイテストと品質確認](プレイテストと品質確認.md)で操作しながら確認する。静止画だけでタイミングや操作感の良し悪しを判断しない。
