# 見た目と音の設計

画面、表示範囲・カメラ、UI/UX、素材、アニメーション、音、演出を作成・変更するときに読む。プレイヤーが何を見て判断し、どう操作し、何を感じるかを画面と反応へ落とす。遊びのための構成を先に決め、装飾の追加だけでゲームらしさを作ろうとしない。

## プレイ画面を遊びから構成する

画面を作る前に、今回の代表場面について次をチャットで短く具体化する。既存画面の部分修正では関係する項目だけ扱う。新規画面や大きな構成変更は[ワイヤーフレームで実装前に確認する](#ワイヤーフレームで実装前に確認する)へ進み、小さな修正では企画書や追加の承認工程を必須にしない。

1. **場面と行動**: プレイヤーがどんな状況で、何を見て、何を選び、何を操作するか。
2. **主役と空間**: 世界、盤面、手札、人物や会話など、遊びが実際に起きる場所と必要な広さ。操作対象、進路、予告、選択結果を見渡せる構成を選ぶ。
3. **視線の流れ**: 最初に見る対象、判断に使う手掛かり、結果を確認する位置。速い判断が必要なら視線の往復を減らし、熟考する遊びなら比較できる情報を揃える。
4. **情報の層**: 常時見るもの、対象を選んだときに見るもの、ポーズや別画面で見るもの。UI要素ごとに「どの判断に必要か」を説明できるようにする。
5. **操作と反応**: 入力場所、選択・決定・取り消し、実行可能な範囲、結果の伝え方。実装するルールと食い違わないようにする。

操作対象と結果の空間的な関係を保つ。対象の状態は可能ならその近くで分かるようにし、別パネルの数値を何度も探させない。ただし移動する対象への表示が重なるなら、固定HUDや選択時表示など読み取れる方式を選ぶ。

| 層 | 役割 | 配置・表示を決める基準 |
| --- | --- | --- |
| プレイの主面 | 移動、配置、解法、選択、会話などが起きる場所 | 今の操作と次の判断に必要な対象・空間を確保する |
| HUD | 体力、時間、資源など、プレイ中に必要な情報 | 見落としの影響と参照頻度で強さ・位置を決め、主面を覆いすぎない |
| 状況に応じた表示 | 対象詳細、行動候補、射程、配置や効果の予測 | 判断が必要なときに対象と結び付けて出し、不要になれば閉じる |
| メニュー | 設定、装備、図鑑など、プレイの流れから離れて扱う情報 | 必要な場面でアクセスでき、戻ったときに状態と操作が分かるようにする |

すべての層を毎回設けない。文字やメニューで遊ぶゲームでは選択肢や文章自体が主面になり、世界を描く画面が必須とは限らない。

## ワイヤーフレームで実装前に確認する

新規ゲームの代表的なプレイ画面、新規メニュー、画面構成・情報の優先順位・UI・カメラの表示範囲を大きく変える場合は、機能実装の前に視覚案を提示し、ユーザーの承認を得てからその案の試作・実装へ進む。確認する対象は配置、見せる範囲、情報の出し方、主な操作の流れとする。

- 最初は遊びの中心となる代表場面を一つ選び、実際の対象解像度・縦横比を意識して世界・盤面・手札・人物などの操作対象と必要なHUDを仮素材で示す。文字や枠だけのメニュー案を、プレイ画面の確認へ置き換えない。選択中、危険時、結果など配置や情報が変わる状態は、判断に必要なものだけ添える。全画面や全ステージを先に設計しない。
- ローカルHTML、画像、利用できる描画・プレビューツールなどで、ユーザーが実際に見られるワイヤーフレームを提示する。世界観、配色、素材感の判断が必要ならモックアップも添える。形式はエンジンに固定せず、文章の説明やファイルパスだけで視覚案を提示した扱いにしない。
- ワイヤーフレーム作成は承認を得るための準備として進める。確認に必要な仮素材・表示に範囲を絞り、本番の画面への組み込み、ゲーム機能、大量の素材制作を先行させない。新しいMarkdown文書を既定で作らず、確認したい点と仮の部分をチャットで短く説明する。
- 視覚案を見せたうえで、実装へ進めるか、どこを直すかをまとめて尋ね、回答を待つ。待機中は視覚案の選択に依存しない調査や準備を進められる。無回答や時間経過を承認とみなさない。視覚案を表示できない場合は制約を伝え、確認方法を合意してから依存する実装へ進む。
- 誤字、軽微な余白・色の調整、画面構成を保つ不具合・数値・操作感の修正、承認済みの構成を使う追加ステージでは再承認を必須にしない。実装用として明示的に承認された既存案は、対象の画面構成と操作の流れを含む範囲で再利用する。「事前確認なしで実装して」などの明示指示を優先するが、デザインを任されたことだけでは確認を省略しない。
- 承認後の細かな調整で繰り返し止まらない。試作の結果や技術的な制約で、承認された主面、画角、情報の優先順位、操作の流れが大きく変わる場合は、理由と変更後の視覚案を示して再確認する。

静止画では移動、ジャンプ、攻撃の反応、カメラ追従、テンポ、面白さを確認できない。視覚案の承認を体験の検証済みという意味にせず、その後の最小の試作を実際に操作して確かめる。動きや時間の変化が配置に影響する場合は、必要な状態の図で意図を示し、試作で成立を確認する。

## 見せる範囲と見せない範囲を決める

画面は、その瞬間のプレイヤーの判断と体験を中心に構成する。配置したオブジェクト、素材、情報をすべて同時に見せることを完成条件にしない。主役の大きさ、操作距離、判断に必要な範囲、文字や操作対象の読み取りやすさから画角と配置を決める。

代表場面の要素を、次の役割へ分ける。役割はプレイ状態に応じて変わり、ファイルやオブジェクトの種類だけで固定しない。

| 役割 | 表示の扱い |
| --- | --- |
| 今の操作・判断に必要 | 読める大きさと位置、必要な予告時間を確保する |
| 必要な場面で使う | 対象選択時、メニュー、別画面、切り替えなどで見せ、使い方を見つけられるようにする |
| 空間や雰囲気を作る | 現在の判断を妨げない範囲で、画面外、重なり、部分的な見切れを許容する |

- 全要素を収める目的だけで、カメラを引く、ズームを下げる、画角を広げる、対象や文字を縮小する変更を行わない。対象・装飾・パネルが増えたことを、全体が収まる画角へ自動調整する理由にしない。
- 背景、周辺地形、装飾、現在関係のない対象は、完全に見える必要がない。画面外にも世界が続く構成を許容し、見切れだけを不具合として修正しない。見せないことと、元のゲーム内容や機能を削除することを区別する。
- 操作対象、判断に必要な手掛かり、危険の予告を、隠す・重ねる・小さくすることで読めなくしない。画面外から影響が来る場合は、遊びのルールに合う予告、表示範囲、手掛かりを選び、予測や回避の機会のない失敗を生まないようにする。
- 詳細や補助機能は必要なときにアクセスできる表示へ分ける。ウィンドウや縦横比が変わる場合も、全表示のための一括縮小を既定値にせず、判断に必要な範囲、配置、情報の出す時機を見直す。
- 盤上ゲームなど全体を見渡すことが判断に必要な場合や、ユーザーが全体表示・全要素の再現を明示した場合は、その要件を優先する。全体が必要な理由を確認し、読み取りや操作を保つ配置・表示方法を選ぶ。

例えば横スクロールのアクションでは、プレイヤー周辺と判断に必要な前方を見せ、ステージ全体を縮小して収めない。盤面全体から次の手を選ぶゲームでは、その盤面を必要な判断範囲として扱う。全体図とプレイ時の表示が両方必要なら、用途に応じて切り替えるなど、異なる役割として設計する。

## 業務アプリの構成をそのまま使わない

サイドバー、ページ見出し、説明文、大きな指標カード、一覧、管理パネルを先に並べ、その余りに小さなプレイ領域を置く構成を既定値にしない。再利用するUI部品やWebの実装方式が、ゲーム全体の画面構成を決めないようにする。

| 業務アプリへ寄りやすい設計 | ゲームの体験から組み直す方向 |
| --- | --- |
| 体力・得点・時間を同じ大きさの指標カードで並べる | 判断の緊急度と頻度に合わせてHUDへ置き、変化があった情報を必要な強さで伝える |
| 盤面や世界を説明カードの中の小さなプレビューにする | 盤面や世界を実際の操作・判断の中心にし、説明は開始時や必要な場面へ移す |
| すべての操作を常設の管理パネルへ集める | 対象選択、手札、道具、文脈に合う操作へ結び付け、使える行動と結果を予測できるようにする |
| 攻撃・獲得・失敗を通知やログだけで伝える | 行動が起きた場所の変化、動き、音と必要なHUD更新で結果を伝える |
| 角丸、影、カードの反復を画面全域へ適用する | 遊びのまとまりと作品の形・質感に合わせて、境界を持つ場所と一続きの空間を選ぶ |

カード、表、ボタン、パネルを一律に禁止しない。カードゲームの手札、経営ゲームの比較表、戦略ゲームの指揮パネルは、選択や駆け引きを生むなら主面や操作の一部として使える。「業務アプリにある部品か」ではなく、「この位置・大きさ・表示時間が遊びを支えるか」で判断する。

UIをゲームらしくするために、依頼されていない3D化、描画方式の変更、大量の素材生成やエフェクト追加を行わない。最初に主面の扱い、情報の優先順、操作のつながりを修正する。

## ジャンルと判断速度に合わせる

次は配置を考える例であり、固定テンプレートではない。ユーザーの指定と既存の遊びを優先する。

- **アクション**: 操作キャラクター、進路、危険の予兆を見渡せる空間を中心にする。プレイ中に長文や管理パネルへ視線を移させず、重要な反応を行動の場所と結び付ける。
- **パズル・盤上**: 解法を考える盤面と選択状態を中心にする。動かせる対象、移動先、手順や資源への影響を読み取れるようにし、関係する状態を離れた指標へ分散させない。
- **カード・戦略・経営**: 手札、配置、資源、候補の比較を遊びの構造に沿って置く。情報を減らすことだけを目標にせず、手番・選択・予測・決定の関係を明確にする。
- **物語・会話**: 今見ている場面、人物、台詞、選択肢の関係を中心にする。進行操作を迷わず扱え、履歴や設定から話の文脈へ戻れるようにする。

読み取る時間、判断する時間、操作する時間を区別する。表示を短くしすぎて判断材料を消さず、重要な選択や結果を読む前に次へ進めない。反対に、確認済みの演出や反復する案内で毎回プレイを待たせない。

## 体験に合わせて方向を決める

既存作品や指定された参考の、情報の優先順、色・形・質感、画面密度、動き、音の役割を確認する。ジャンル名だけでピクセルアート、ネオン、派手なエフェクトなどへ固定しない。

方向が未定で仕上がりに大きく影響する場合は、遊びと目的に結び付く少数の案を提示する。指定がある場合はその方向を具体化し、通常の細かな素材・配置・タイミングで承認を繰り返さない。

世界・盤面・UIが同じ作品に見えるよう、形、素材感、線、色の役割、文字、動きの基準を少数選んで一貫させる。装飾書体や背景の細部は、数字や選択肢の読み取りと競合しない場所へ使う。すべてを同じ枠へ入れて統一したことにしない。

実際のプレイ対象を使った代表場面で、通常時に加え、今回重要な選択中・危険時・結果などの状態を比べる。背景画像、ロゴ、静止した見出しだけの見本から、ゲーム画面としての構成を判断しない。参考作品は枠や色の模倣だけでなく、視線、情報の出し方、操作と反応を分析する。

## 判断に必要な情報を見せる

- プレイヤー、操作対象、目標、危険、獲得できるものを、色だけでなく形・位置・動きなどでも見分けられるようにする。
- HUDには今の判断に必要な値を優先する。数値が変化した理由と、次に取れる行動が分かる表示を選ぶ。
- 情報の常時表示・場面限定表示は[見せる範囲と見せない範囲](#見せる範囲と見せない範囲を決める)の役割に従う。表示が増減しても主要な操作位置と重要情報が不意に動かないようにする。
- 操作説明は実際の割り当てと対応させ、プレイを始めるための情報を最初に出す。必要な場面で説明を増やし、全ルールを長文で一度に提示しない。
- メニューとダイアログはフォーカス、選択、決定・戻るの反応を確認する。マウスを使わない入力が対象なら、その方式で最後まで操作できるようにする。
- 対象解像度、縦横比、文字の長さ、表示言語、端末の安全領域に合わせて配置を確かめる。拡大縮小したときの文字・操作領域・ゲーム内座標の関係を扱う。

ゲーム内の情報と、開発用のデバッグ表示や内部構成の説明を区別する。開発者向け情報をプレイヤーの通常画面へ残さない。

## 操作の見通しと画面間の流れを作る

操作対象、選択中のもの、実行可能な行動、実行後に起きる変化を見分けられるようにする。選択と実行を区別するゲームでは、その状態を保ち、意図しない決定や入力の持ち越しを防ぐ。配置、射程、費用などの予測表示は実際のルールと同じ条件を使う。予測できないことが遊びの一部なら、既知の情報と不確実な範囲を区別する。

戻る・取り消す・閉じるの役割を揃え、操作できない理由を必要な場所で伝える。ホバーだけで重要情報を出さず、対象入力に合わせた確認方法を用意する。タッチでは指で隠れる領域と押し間違い、ゲームパッドではフォーカスの移動、キーボードでは操作表示と実際の割り当てを確認する。

画面は個々のレイアウトに加え、プレイ前後のつながりを設計する。今回必要な状態だけ扱う。

| 場面 | 体験として確認すること |
| --- | --- |
| タイトル・開始 | 遊ぶための次の操作が明確で、設定や説明を読まないと始められない構成になっていないか |
| 最初のプレイ | 核となる操作と反応を、安全に試しながら理解できるか |
| プレイ中 | 目標、操作対象、判断材料、結果がつながり、意図した判断速度で扱えるか |
| ポーズ・別画面 | 操作の意味とゲームが止まる範囲が明確で、戻ると元の判断を続けられるか |
| 結果・再挑戦 | 何が起きたかが分かり、再挑戦や次の行動へ必要な手順で進めるか |

チュートリアルは最初の意味ある行動と反応へ結び付け、説明カードを読み進めるだけで習得した扱いにしない。スキップや後からの確認は遊びと制作範囲に応じて用意する。反復プレイでは、再挑戦のたびに同じ説明・長い演出・深いメニュー操作を強制しない。

## 行動と結果の反応を組み立てる

重要な行動について、入力の受理、予兆、実行、成功・失敗、その後の状態をどう見せるかを考える。すべての段階に効果を付けるのではなく、分かりにくい箇所と体験の見せ場へ集中する。

| 目的 | 確認する関係 |
| --- | --- |
| 操作の反応 | 入力を受理した時点と画面の反応が合っているか |
| 危険の予告 | 回避や判断が必要な時間に、必要な情報が見えるか |
| 成功・失敗 | 判定と表示・音が一致し、色や音だけに依存していないか |
| 重みや勢い | 動き、音、カメラの反応が狙った感覚を支えているか |
| 次の行動 | 演出の待ち時間や表示の重なりが操作を妨げていないか |

ヒットストップ、画面の揺れ、残像、点滅などを使う場合は、目的と実際の変化を短く説明する。すべてのゲームで使う前提にせず、強度、頻度、操作への影響を確認する。強い揺れや点滅、重要な音には、必要に応じて低減・代替表示・音量調整を用意する。

演出中も、入力を受け付けるか、待つ必要があるか、次の操作がいつ可能かを明確にする。演出を省略・低減した場合も必要な情報と結果が残るようにし、装飾を減らすと遊べなくなる作りにしない。

## 素材を制作し、ゲームへ組み込む

既存・提供素材を確認し、足りない用途に合う素材を用意する。生成ツールが利用可能なら使えるが、任意のサービスを必須にしない。

スプライトなら透過、基準点、サイズ、向き、コマ間の一貫性、3D素材ならスケール、座標、マテリアル、リグなど、組み込みに必要な条件を先に決める。見栄えの良い一枚絵を、アニメーションや当たり判定にそのまま使える素材とみなさない。

UIの重要な文字や数値は、変更・翻訳・読みやすさに対応できるゲーム側の表示を優先する。素材を取り込んだ後、実際の背景、縮尺、動きの中で見え方を確認する。描画・読み込み負荷とメモリ量は対象環境に合わせて測る。

素材の出典と利用条件を、プロジェクトの既存の管理方法に合わせて保持する。出所不明の素材を配布物へ混ぜない。仮素材を使った確認と最終素材での確認を区別する。

## 音を画面と合わせる

行動音、環境音、BGM、声の役割を決め、同時に鳴る場合の優先順と音量を調整する。連打や多数の敵で効果音が重なり続ける場合は再生数や頻度を扱い、音の停止・フェードを状態遷移と合わせる。

音の再生開始にユーザー操作が必要な環境では、実際の起動から試す。ポーズ、ミュート、画面切り替え、再開始で意図した再生状態になるかを確かめる。再生できる手段がない場合は、音を聞いて確認したことにしない。

画面と音の反応は[プレイテストと品質確認](プレイテストと品質確認.md#ゲーム画面としてのuiuxを確認する)で操作しながら確認する。静止画だけでタイミングや操作感の良し悪しを判断しない。
