# 制作環境の選択

制作基盤が未定、移行や対象端末の追加が必要、環境別手順を追加するときに読む。企画のジャンル名や2D・3Dだけでエンジンを決めない。

## 既存環境を先に確認する

既存ゲームでは、プロジェクト設定と依存情報から、エンジン・ライブラリの実際のバージョン、対象環境、起動・ビルド・テスト方法を確認する。ランタイムやエディタが使えること、対象端末で試せることは別に確認する。

指定エンジンや既存実装で依頼を満たせるなら再利用する。新規ゲームでもユーザーの指定を優先する。困難がある場合は不足する機能や環境を具体的に示し、別の環境へ勝手に置き換えない。

## 未定の場合に比較する

実際の要件に合う少数の候補を、次の観点で比較する。製品の網羅的なランキングは作らない。

| 観点 | 判断材料 |
| --- | --- |
| 配布先 | ブラウザ、デスクトップ、モバイルなど、今回必要な対象 |
| 遊びと描画 | 物理、2D・3D、文字・UI、音、ステージ編集など必要な機能 |
| 既存資産 | コード、素材、編集データ、利用者が扱える制作環境 |
| 作業と検証 | 使用できるエディタやCLI、画面操作、テスト、実機確認の方法 |
| 維持と配布 | ビルドの再現性、依存関係、ライセンス、配布先の条件 |

標準機能と既存依存で満たせる範囲を確認し、追加ライブラリや自作の仕組みを選ぶ理由を示す。画面がWebであることだけを理由に、通常のサイト構築へゲームループや入力処理を押し込まない。反対に、軽いターン制の遊びへ重いリアルタイム基盤を必須にしない。

新しい依存、アーキテクチャ、外部APIやデータ保存の判断では、適用される調査ルールに従う。`implementation-researcher`が利用可能なら活用できるが、必須の外部依存にはしない。使えない場合も標準機能・既存依存・代案を比較する。

版に依存するAPI、サポート対象、書き出し条件、ライセンスは、そのプロジェクトで使う版の公式資料を確認する。最新の推奨を無条件に既存プロジェクトへ適用せず、移行を依頼されていなければエンジン更新を作業に混ぜない。

## 実行能力の不足を扱う

- コードを編集できることと、エディタ・GUI・対象端末を操作できることを区別する。
- GUIを使えない場合はCLIで確認できる範囲を調べる。headlessでの起動やテストは実際の操作感・音・描画の確認を代替しない。
- エンジンやSDKがない場合、既存の導入先と利用可能な手段を確認する。利用許諾、追加費用、システム変更が必要な導入を自動で進めない。
- できる実装・静的検査を進め、実行確認に必要な環境と未確認項目を説明する。「環境がない」だけで他の制作方式へ変更したり、テスト済みと報告したりしない。

## 環境別手順を追加する

初版は共通手順だけを持つ。実際に環境固有の再利用可能な手順が必要になったとき、`references/engines/<environment>/`へ必要な資料を追加する。`<environment>`には`godot`、`unity`、`browser`など英語名を使うが、すべてを先に作らない。資料名は内容が分かる日本語にする。

資料には次の情報を必要な範囲でまとめる。

1. 対象バージョンと適用条件、確認した公式資料。
2. プロジェクト構成を見分ける方法と、既存設定を優先する箇所。
3. 実行・テスト・ビルドの確認方法と、使用できるツールの条件。
4. 入力、時間、物理、資源の寿命など、共通手順を具体化する環境固有の注意点。
5. 実際に検証した範囲と、版や対象端末に依存する制約。

追加した資料は`SKILL.md`の参照案内へリンクし、その環境の作業時だけ読む条件を記す。共通の企画、演出、品質基準はコピーせず、それぞれの資料を参照する。環境別フォルダへ別の`SKILL.md`は置かない。

繰り返し実行する処理が明確になったら`scripts/`へ英語名のヘルパーを置き、対応環境、引数、副作用、失敗条件をその環境の資料で説明して代表ケースを検証する。固定のスターターや素材を配布する実用途ができたときだけ`assets/`を加え、出典とライセンスを保持する。
