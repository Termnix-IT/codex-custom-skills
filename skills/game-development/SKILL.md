# ゲーム制作

プレイヤーが何を判断し、何をすると、どんな変化を感じるゲームなのかを軸に、今回依頼された範囲を制作する。機能数や見た目の完成度だけで遊べる状態を判断しない。

## 依頼と現在地を確認する

- 新規制作、既存ゲームの変更、企画相談、演出調整、検証、ビルドのどれが必要かを判断する。既存ゲームの小さな修正を企画からやり直さず、相談だけの依頼で実装を始めない。
- 指定されたエンジン、言語、対象端末、入力方法、ジャンル、参考作品、素材、制作規模を優先する。既存プロジェクトでは指示、起動方法、バージョン、シーンやステージ、入力・状態・保存の実装、関連テストを必要な範囲で確認する。
- ゲームの核、対象環境、今回の完成範囲を左右する不足だけ質問する。判断できる項目は仮定を短く示して進め、承認済みの工程や通常の実装判断で再確認して止まらない。
- 企画から配布まで対応できることと、毎回全工程を実施することを区別する。制作範囲にないオンライン対応、課金、分析基盤、ストア公開を追加しない。

## 遊べる単位で進める

新規画面やUI/UXを設計するときは、[見た目と音の設計](references/見た目と音の設計.md#プレイ画面を遊びから構成する)を読み、プレイヤーが見る・選ぶ・操作する対象を画面の主役にする。サイドバー、指標カード、管理パネルなど業務アプリの構成を既定値にせず、盤面・世界・手札・会話など今回の遊びから配置と情報の出し方を決める。

1. 今回作る体験と、実行・操作して確認できる完成条件を短く共有する。新規制作では、核となる行動から結果・次の行動までを体験できる最小の試作を先に選ぶ。
2. 必要な操作、ルール、状態の変化を一つの流れとして実装する。試作で確かめる項目を限定し、コンテンツの量産や共通基盤の拡張を先行させない。
3. 実際に操作し、反応、分かりやすさ、選択の意味、終了・再開など今回の範囲に関係する挙動を確かめる。試作が目的を満たさなければ、原因に関係するルールや情報を調整する。
4. 依頼が完成版を含む場合は、試作で得た結果を反映して必要なコンテンツと演出を仕上げ、対象環境で検証する。試作で終えて完成版の依頼を満たしたことにしない。
5. 配布を依頼された場合は、配布物そのものを検証して引き渡す。成果物、起動・操作方法、確認できた範囲、残る制約を簡潔に伝える。

既存ゲームの変更はこの流れの該当部分から始める。自動テスト、静止画、ビルド成功はそれぞれの証拠として扱い、実際に遊べたことや面白さの確認へ置き換えない。

## 方針と環境への適応

- 特定エンジンのAPI、ファイル構成、物理更新、座標規約を共通ルールへ埋め込まない。既存の仕組みを使い、版に依存する判断はプロジェクトのバージョンと公式資料を確認する。
- 他のSkillや生成サービスは、利用可能で今回の工程に役立つ場合だけ使う。このSkill単体でも制作判断ができるようにし、外部Skillの一括導入を前提にしない。
- 制作中の決定はチャットで共有し、継続作業に必要な仕様や再現手順は既存の適切な場所へ反映する。企画書、制作日誌、テスト報告などのMarkdownを毎回自動生成しない。
- 再利用できる環境別手順が必要になったら、[制作環境の選択](references/制作環境の選択.md#環境別手順を追加する)に従って追加する。実用途のない`engines/`、`scripts/`、`assets/`や空の雛形は作らない。
