# 編集と確認のポイント

## 演出の選び方と説明

方向性の提案では、構成の作り方と、映像・文字・音に使う技法を内容に応じて紹介する。下表は候補の例であり、毎回提示するメニューや全機能の一覧ではない。素材で実現でき、目的に寄与するものを選び、「この手法をこの場面に使うと、何が伝わりやすくなるか」まで説明する。使用頻度や派手さだけを推奨理由にしない。

| 技法 | ユーザーへの説明例 | 編集上の判断 |
| --- | --- | --- |
| モーショングラフィックス | 「文字・図形・線・アイコンを動かし、機能の関係や工程の流れを分かりやすく見せます」 | 元資料にある関係と順序を動きに対応させる。情報を段階的に見せ、理解・読み取りの時間を確保する |
| キネティックタイポグラフィ | 「言葉の意味や語りに合わせて文字を動かし、重要なメッセージを印象に残します」 | 文章主体の紹介に向く。読む時間を確保し、動きだけを目的にしない |
| モンタージュ | 「特徴的な場面を短くつなぎ、作品の魅力や勢いをまとめて見せます」 | 複数の見せ場が必要。操作の理解が目的なら必要な前後の流れを残す |
| マッチカット | 「似た形や動きを合わせて場面を切り替え、内容のつながりを感じさせます」 | 対応する構図や動きがある素材を選ぶ。単なる高速切り替えとは区別する |
| パララックス | 「前景と背景を違う速さで動かし、静止画にも奥行きを感じさせます」 | 分けられるレイヤーと移動用の余白が必要。隠れた部分の欠けや透明な縁を確認する |
| 分割画面・前後比較 | 「二つの状態を並べ、違いや変化を一目で分かるようにします」 | 比較対象・倍率・時点をそろえる。変化の事実は元資料で確認する |
| 操作から結果へ見せる構成 | 「何をして何が起きるかを順に見せ、使い方と価値を伝えます」 | 実際の操作と結果が分かる素材を使う。説明に必要な時間を過度に縮めない |
| パンチイン | 「瞬間的に拡大して、命中した瞬間に視線を集めます」 | 短い区間だけ拡大する。HUDや操作対象を切らない |
| スピードランプ | 「前後は速く、決定的な瞬間はゆっくりにして強調します」 | 前後の動きを確認して速度を変える。低fps素材の強いスローは滑らかにならない |
| ビートに合わせたカット | 「BGMのリズムに合わせて場面を切り替え、勢いを出します」 | 拍位置を実際の音や波形から確認する。等間隔のカットだけで拍合わせと呼ばない |
| クロスフェード | 「前の映像が薄れながら次の映像が現れ、穏やかにつながります」 | 重なりで全体の尺が短くなる。音のつなぎ方も合わせて設計する |
| 画面揺れ | 「衝撃の瞬間に画面を少し揺らし、強さを感じさせます」 | 短く抑え、余白を確保する。操作や字幕の読み取りを妨げない |
| 色調整 | 「色と明暗をそろえ、場面が変わっても統一感を出します」 | アプリ紹介ではUIの実際の色や文字の判別を保つ |
| ダッキング | 「話している間だけBGMを下げ、声を聴き取りやすくします」 | 効果音で誤って音楽を下げず、声の間で音量が不自然に上下しないか聴く |
| ヒット音 | 「大事な言葉や瞬間に短い衝撃音を合わせ、印象を強めます」 | 連発せず、画面の動きとの位置と音量を確認する |
| 音を引く・無音 | 「見せ場の前に音を一度抑え、次の瞬間を際立たせます」 | 意図した間を作る。単なる音声欠落とは区別する |

全部の演出を使わない。見せたい内容と素材に合うものを選ぶ。PVは特徴と見せ場の構成、キル集は前後の流れと衝撃、アプリ紹介は操作と結果の分かりやすさを重視する。これらを固定テンプレートとして強制しない。

モーショングラフィックスは、例えば「線が伸びて要素を結ぶ」「アイコンが順に並び工程を示す」「図形の大きさが変わり、根拠のある数値の変化を示す」と提案できる。文字中心のキネティックタイポグラフィもこの表現に含まれる。Pythonで簡単な図形・線を描き、要素の位置・大きさ・透明度・表示順・動きの加減速を制作データで調整し、FFmpegで合成・書き出しする。動きが何を意味するかを決め、装飾だけで機能・因果関係・数値を作り足さない。専用ソフトや画像生成を必須にしない。

## 演出案と短いプレビュー

案の違いは「何を主役にし、どんな流れと音で見せるか」で説明する。例えば紹介動画なら、言葉と語りで価値を伝える案、操作と結果で体験を見せる案、印象的な場面を音楽でつなぐ案が考えられる。素材が支えられない案は出さず、どれにも同じ構成を当てはめない。

各案には採用候補の手法と、その用途・推奨理由を結び付ける。例えば文章だけの紹介なら「キネティックタイポグラフィで要点を語りに合わせて動かすと、説明の軸を印象に残せます。挿絵に奥行きを付けたいならパララックスも合いますが、前景・背景を分ける素材が必要です」と助言できる。操作動画なら結果の理解、キル集なら決定的な瞬間の強調など、今回の素材へ理由を置き換える。説明済みの手法は案ごとに繰り返し定義せず、同じ名前でも使う場面と役割の違いを示す。

選択後は、強みが伝わる代表場面を動きと音付きで制作する。目立つ場面だけでなく、その前後の間や説明とのつながりが判断できる範囲を含める。確認時は「この方向で全編を進めてよいか」を尋ね、読みづらさ、迫力、落ち着き、声など感覚的な返答を受け付ける。時間経過や選択肢の消失を確認済みと扱わない。

全編の確認では、文字を読み切れるか、視線が迷わないか、場面ごとの変化が内容を伝えるか、強みへ十分な尺を使ったかを評価する。文字・図・BGMが動くことだけを演出の完成と扱わない。

## 生成画像を動画へ組み込む

演出案で採用された背景・挿絵・透過素材だけを用意する。画像の役割と生成・修正の上限が合意済みなら、その範囲で進める。生成画像を使わない案も、素材と目的に応じて選べるようにする。

- **入力と構図**: 参照画像、編集対象、合成する素材の役割を区別し、入力画像を実際に確認する。動画の縦横比、トリミングや移動に使う余白、文字を置く空間、配色・画風を指示に含める。複数画像の統一には共通の指定と採用済みの参照画像を使い、不要な被写体や設定を加えない。
- **生成手段**: GPT Imageを利用できる組み込み画像生成ツールを優先する。組み込みツールにAPIキーを要求しない。利用できない場合は、提供素材やPythonで描く文字・図による代案を示す。API・CLIはユーザーが選択した場合だけ使い、利用可能なモデル・引数・料金を現行の公式資料で確認する。`OPENAI_API_KEY`は環境変数から取得し、チャットや制作データへ含めない。合意外の生成や別モデル・サービスへの切り替えをしない。
- **保存と再利用**: 採用した画像を制作物の出力先へコピーし、生成先の一時的な場所だけを参照しない。用途、生成・編集の指示、参照素材、実際の生成手段、生成回数を修正用の制作データへ残す。既存素材を保持し、修正版は別名で保存する。採用した画像を全編でも再利用し、変更が必要な素材だけ上限内で修正する。
- **画像の確認**: 被写体、形状、画風の一貫性、構図、合成時の切れを画像として確認する。透過素材はPNGなどで透明度を保持し、白背景や市松模様を透過と取り違えない。名称・説明文・既存ロゴは別のレイヤーで元資料に合わせて配置する。生成画像を実際のUIやゲームプレイの代わりに見せない。
- **映像としての確認**: 拡大・移動・重なりはPythonとFFmpegで設計し、動かした後の余白・画質・透明な縁・字幕の可読性を音付きプレビューで確認する。画像を連続生成するだけで滑らかな動画になるとは扱わない。例えば「レイヤーごとに速度を変えて動かし、奥行きを感じさせます」と、目立つ動きの目的を短く説明する。

## FFmpegで追加処理するとき

- Pythonの`subprocess.run`には引数のリストを渡し、`shell=False`で実行する。長いフィルターにはフィルタースクリプトや字幕ファイルを使い、Windowsのパス・日本語・引用符をテキストへ直接埋め込む処理を減らす。
- クロスフェードでは解像度、fps、timebase、pixel formatをそろえる。重なりによる尺の変化を字幕・音声の時間軸へ反映する。
- 速度は映像の`setpts`と音声の`atempo`を対応させる。原音を残すか、見せ場の効果音として別配置するかを目的に応じて決める。
- 効果音は完成動画の時間軸へ置き、BGM・原音と混ぜた結果を確認する。音割れ防止だけで聞きやすい音量が保証されるとは扱わない。
- 字幕は安全な余白に置き、長文を読める長さにする。タイトルや機能名の誤字は元資料と照合する。
- `drawtext`のフォント自動検出が失敗する環境では、存在するフォントを`fontfile`で明示する。システム設定を変更せず、日本語の表示を抽出フレームで確認する。

## 確認する箇所

- 冒頭・末尾、各カットの直前直後、速度変化、拡大、字幕の出入り。代表フレームだけでは動きと音の同期は確認できない。
- 黒い隙間、意図しない余白、縦横比の変形、画質低下、重要なUIの切れ、字幕とHUDの重なり。
- 音の開始、原音とBGMのバランス、効果音の位置、つなぎ目、末尾の切れ方。再生確認ができない場合は未確認と伝える。
- 元素材にない成功や機能を、字幕や演出で事実のように追加していないか。
