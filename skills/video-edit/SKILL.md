# 動画の編集・制作

提供された素材を、依頼の意図に合わせて編集する。名前・概要など文章だけの紹介依頼では、内容を確認し、モーショングラフィックス（文字・図形・線・アイコンなどに動きを付ける表現）で動画を制作できる。PV、キル集、アプリ紹介は用途の例であり、ジャンルや尺を固定しない。必要ならGPT Imageで背景・挿絵・透過素材を補い、repoからの撮影も依頼に必要な場合だけ追加する。

## 依頼を編集方針にする

- 素材、目的、必須の場面、尺・縦横比、残したい音、参考作品を確認する。依頼や素材から判断できる項目は仮定を短く伝えて進め、結果を左右する不足だけ質問する。編集技術の選択をユーザーへ丸投げしない。
- **見せ方（文字中心・バランス・動き中心）、動きの強さ（控えめ・強め・過剰）、言葉の優先（業務向けの説明・動画映えする短い言葉・両立）**を演出方針に含める。依頼・参考作品・会話で明確な項目は再質問せず、不足する項目を案の選択と一緒に確認する。三つは独立して扱い、「正確な業務説明を強く動かす」などの組み合わせも受け付ける。Web方式を選んだだけで動きが強くなると判断しない。
- 素材を確認したうえで、印象に残す強みと視聴者に伝えたい感覚を決め、**異なる演出方向を2〜3案**提示する。各案には強み、主役・構成・テンポ、上記の三項目、具体的な代表場面、音の方向、情報の要約方針、優先することと抑えることを含め、推奨案と理由を添える。色や効果だけを変えた案にしない。ユーザーが選ぶまで方向に依存する制作を進めず、案の組み合わせも受け付ける。[演出案と短いプレビュー](references/編集と確認のポイント.md#演出案と短いプレビュー)の質問例を素材に合わせて使う。
- **方向性を選ぶ前に**、一般的な構成・編集手法から素材と目的に合うものを少数選び、名前、見える・聞こえる変化、今回どこで何をより表現できるかを短く示す。各案の代表場面と結び付け、推奨する使い方・組み合わせの理由を助言する。必要な素材や表現上の制約がある場合は併せて示す。[演出の選び方と説明](references/編集と確認のポイント.md#演出の選び方と説明)を参考にし、技法一覧を丸ごと提示したり、専門用語だけで比較したりしない。ユーザーは表現したい印象から案を選べるようにし、技法を一つずつ選ぶことを求めない。
- 参考作品は文字の扱い、画面構成、展開、音との関係を分析し、素材に応用する。静けさや明快さも強みになる。特定の配色・書体・派手さをすべての動画へ強制しない。
- 原文の意味と必須情報を守り、選んだ言葉の優先に沿って要約・言い換え・並べ替えをAIが行う。動画映えを優先する場合は短句、動詞、語りに合わせた分割へ整え、元の説明と動画内の文言の対比例を案に添える。長文を固定配置して入退場だけ動かす構成に頼らない。意味を変える省略や、資料にない機能・効果・成功を追加しない。原文維持の指定や必要な注意事項は優先する。
- 目立つ演出、初めて説明する技法、仕上がりを左右する効果には、**名前＋見える・聞こえる変化＋今回の目的**を1〜2文で説明する。例：「パンチイン（瞬間的な拡大）を決定的な場面に使い、視線を集めます」。通常のカットや音量調整まで列挙せず、同じ技法を繰り返し説明しない。
- 説明はチャットで行い、動画内に技術解説を入れない。選択後の細かな技法はAIが判断し、一つずつ承認を求めない。「勢いを増やして」「揺れは控えめに」など感覚的な修正を受け付ける。選択した方向を大きく変える必要があれば相談する。

## 素材を確認する

1. 既存の制作プロジェクト、指定された方式、利用可能なランタイム・描画基盤を確認する。FFmpeg・ffprobeは素材検査と完成動画の検証に使う。同梱ヘルパーを使う場合はPythonも確認し、Web方式の必要環境は[Web方式の制作](references/Web方式の制作.md)で確認する。見つからない場合は既存の実行ファイルやランタイムを確認し、自動でシステム設定を変更しない。
2. 動画・画像・音声素材は`scripts/video_workflow.py inspect`またはffprobeでストリームや尺を調べる。文章素材は元資料を読み、名称・概要・必須情報を照合する。元素材を保持し、[保存先と個人設定](references/編集と確認のポイント.md#保存先と個人設定)に従って出力場所を決める。今回の指定を優先し、なければ任意のローカル設定を確認する。
3. 動画素材は`frames`またはFFmpegで確認用のフレームを抽出し、利用可能な画像・動画閲覧手段で実際の内容を確認する。静止画像は画像として確認する。抽出成功だけを内容確認として扱わない。長尺は粗く探索し、候補の前後を細かく確認する。
4. キル判定や操作の成功などは、HUD、直前直後の動き、音、指定されたタイムスタンプを根拠に判断する。画面変化の検出や少数の静止画だけで意味を断定しない。判断できない場合は候補として示すか、該当場面を質問する。

## 制作方式を選ぶ

素材確認後、演出案を作る段階で主方式と必要な補助方式を仮選択し、方向性の選択後に必要環境を確認して確定する。ユーザーの指定と既存プロジェクトを優先し、ジャンル名や派手さだけで決めない。

| 方式 | 選ぶ条件 | 読む手順 |
| --- | --- | --- |
| Python＋FFmpeg | 既存映像・音声の編集が中心。カット、速度、音量、字幕、簡単な文字・図形で目的を満たせる | [実行手順](references/実行手順.md) |
| HTML/CSS | 文字・図形・カード・UIの画面構成と動きが主役。Reactを必要とする理由がない | [Web方式の制作](references/Web方式の制作.md)。HyperFramesを第一候補にする |
| React | 共通部品、データからの画面生成、内容違いの量産、既存React資産の利用が重要 | [Web方式の制作](references/Web方式の制作.md)。Remotionを第一候補にする |
| 組み合わせ | 主方式だけでは必要な表現を作りにくい。例えば実写編集に凝った図解・タイトルを加える | 採用した方式の手順と[方式をまたぐ制作](references/編集と確認のポイント.md#方式をまたぐ制作) |

- 同じ成果を得られるなら、既存の基盤を再利用し、依存関係と受け渡しが少ない方式を選ぶ。簡単な編集へWeb方式を強制せず、複雑な描画・時間管理の自作を避けるために既存フレームワークを使う。選ばれた方式の詳細だけを読む。
- 方式と理由は制作データへ残す。ユーザーには仕上がり、修正のしやすさ、費用への影響を短く伝え、技術方式の選択を丸投げしない。承認済みの演出案を外部Skill側で一から聞き直さない。
- 選んだ基盤がない場合は、必要条件、導入範囲、表現への影響を示す。案件の承認範囲で必要な依存だけを用意し、外部Skillの一括導入やシステム設定の変更へ広げない。利用条件・費用・権限が未合意の操作は確認し、大きく異なる代替へ黙って切り替えない。

## 構成と制作

- 選ばれた強みに画面・尺・音を割り当て、各場面の役割から構成と動きを決める。複数の項目を別の視点で紹介する依頼では、主役、情報の順序、画面構成、テンポを内容に応じて変える。全項目を同じレイアウト・同じ尺に並べ、図や色だけ変えて演出の違いとしない。全体の書体・色・動きには一貫性を持たせる。
- 動き中心・強め以上の案では、文字も場面の主役として扱い、大きさ・位置・行分け・表示順を意味や音に合わせて変える。拡大、弾み、画面をまたぐ移動、形の変化、場面転換を代表場面で具体化し、一定の資料レイアウトへ装飾だけを足して終えない。重要な言葉を読み取れる間と、動きの緩急を確保する。
- 素材の使う区間、順序、強調、テキスト、音の扱いを編集可能なJSONや制作プロジェクトへ残す。[共通の制作記録](references/編集と確認のポイント.md#共通の制作記録)で方式・時間軸・出力を関連付ける。修正時は同じ制作データを更新し、完成MP4の再編集で画質を落とさない。
- 基本のカット、定速の速度変更、中央ズーム、フェード、原音・BGM、時刻指定のナレーション・効果音、BGMのダッキング、字幕合成には同梱ヘルパーを使える。操作方法と制作データは[実行手順](references/実行手順.md)を必要に応じて読む。
- ヘルパーの機能に表現を限定しない。追加処理が小さければPythonとFFmpegで補い、凝った文字・図形・UIの演出は選んだWeb基盤の機能を活用する。[編集と確認のポイント](references/編集と確認のポイント.md)を参照する。
- 音楽の拍位置や見せ場を確認して編集する。速度変更は原音との同期・音程を考慮する。字幕や強い演出でゲームのHUD・アプリの重要な操作を隠さない。
- 既存素材を基本とし、新規素材は必要性と手段を説明する。外部生成の使用と費用上限が合意済みなら、その範囲で進める。必要な入力だけを送信し、素材の公開や合意外の有料生成をしない。

## 必要な画像素材を補う

- 持ち込み素材を優先し、背景・挿絵・見せ場の一枚絵・透過素材が伝わりやすさを改善する場合に、GPT Imageによる生成・編集を演出案へ含める。生成するもの、使う場面、期待する効果、枚数と修正回数の上限を示す。APIを使う場合は費用上限も確認し、合意済みの範囲では繰り返し承認を求めない。画像生成を全動画へ強制しない。
- 利用可能な画像生成ツールを使い、`imagegen` Skillがあればその手順に従う。組み込みツールを優先し、API・CLIへの切り替えは明示的に選ばれた場合だけ行う。生成・保存・確認・合成の詳細は[編集と確認のポイント](references/編集と確認のポイント.md#生成画像を動画へ組み込む)を読む。画像生成の環境がなくても通常の動画編集は利用できる。
- 採用画像を実際に確認して音付きプレビューへ組み込み、全編では再利用する。実際のゲーム・アプリの画面や既存ロゴは元の素材を使い、生成した演出素材を実動作の証拠として見せない。名称・説明文は映像編集側で重ね、生成画像の文字へ依存しない。

## 音を設計する

- 演出案にBGMの雰囲気、ナレーションの有無と話し方、素材音の役割、代表的な効果音や無音の使い方を含める。場面ごとに声・音楽・素材音の主役を決め、全部を同時に強く鳴らさない。
- BGMは持ち込みを優先し、不足時は候補を提案する。案件ごとにAIへ選曲を任せる指定にも対応し、雰囲気、合う理由、入手先・利用条件を示してユーザーの選択後に用意する。素材がないことを理由に、単純な自作音楽を自動で採用しない。
- 曲の盛り上がり・区切り・余韻に構成を合わせる。全カットを拍へ揃えず、効果音と無音には動き・強調・転換の目的を持たせる。体験を伝えるゲーム音や操作音を活かし、終わり方も設計する。
- 必要ならGemini TTSを提案し、実際の声を短いプレビューへ含める。採用した音声は再利用し、修正箇所だけ生成する。原稿、発音、間、生成された尺を確認して映像・字幕を合わせ、説明中のBGMを下げる。TTSを使う場合は[音声生成](references/音声生成.md)を読む。

## repoからの撮影が必要な場合

提供動画があれば撮影を省略する。撮影を依頼された場合は、repoの指示と起動手順を読み、実際に使えるブラウザ操作・録画手段を確認する。用途と主要機能を調べ、デモデータで再現可能な操作を撮影して素材にする。通常の録画と、撮影しやすくするためのアプリ変更を区別し、撮影だけの依頼で本体を変更しない。実際に動作確認した範囲を紹介し、録画や起動ができない場合は必要な録画素材を具体的に伝える。

## プレビュー・検証・納品

- 演出案の選択後、代表的な強みを示す**音付きの短い動画プレビュー**を提示する。5〜15秒を目安に内容で調整し、選んだ強さの動き、文字の配置・展開、書き換えた文言、間・意図した音を含める。静止画や全編の低解像度化だけで代用しない。強み、雰囲気、動きの強さ、言葉の調子・読みやすさ、声や音の好みをユーザーが確認し、必要な修正を経てから全編を制作する。ユーザーが確認を省略すると明示した場合は、その指示を優先する。
- 完成動画をffprobeで検査し、デコードできること、尺・解像度・音声を確認する。代表フレームとカット・速度・字幕の境界を見て、文字切れ、黒い隙間、不自然な切り替えを確認する。音声を再生できる手段があれば音量・同期・終わり方も聞く。
- 視聴できなかった項目は未確認と明示し、書き出し成功を品質確認済みとしない。素材・環境の制約で実現できない演出は説明し、同じ目的に合う代案を使う。
- 技術的な検査に加え、強みが伝わるか、単調さ、視線の流れ、読む時間、見せ場の印象、音の主従を確認する。同じレイアウトが続く、文字が多い、音が常に同じ強さなど、目的を損なう箇所を修正する。
- 動画へのリンクまたは利用可能なプレビュー、主な演出の短い説明、修正用の制作データを渡す。技術用語を覚えなくても修正を頼めるようにする。
